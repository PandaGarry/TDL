# Core Foundation Blueprint — фундамент без постоянных переписываний

Статус: **технический план P0 в реализации**. P0-A–D реализованы:
InputMap/2D-слои пересобраны, примитивы и DefinitionRegistry прошли
hardening, а минимальный WorldState получил версионированный codec и
crash-safe SaveStore. Проверки выполняют собственные headless runners на
Godot 4.7.2 в CI. Подготовлено агентом в рамках Baseline Lock раунда 12. Это не новый дизайн-канон и не обещание,
что внутренние алгоритмы никогда не изменятся. Цель документа —
зафиксировать **стабильные швы архитектуры**, через которые экология,
поселения, бой, экспедиции, моды, Steam-транспорт и будущие акты смогут
добавляться локальными модулями, а не переписыванием всей игры.

Главные источники требований:

- `docs/production/round12_baseline_lock.md` — стек, P0–P3 и бюджеты;
- `docs/design/gdd.md` — GDD v1.0 Core Baseline;
- `docs/tech/architecture.md` — текущий Godot-каркас и ограничения H1.

## 0. Короткий ответ про стек

Для старта **нового большого runtime-плагина не нужно**. Текущего стека
достаточно:

- Godot 4.7.2;
- типизированный GDScript;
- GL Compatibility;
- Godot MultiplayerAPI + `ENetMultiplayerPeer` за нашим интерфейсом;
- собственные JSON-определения, реестр, симуляция, сейвы и репликация;
- GitHub Actions с настоящим Godot 4.7.2.

Пригодятся не «ещё плагины», а инженерные контуры вокруг Core:

- тесты GdUnit4 6.2.x после проверки на 4.7.2 и собственный soak-runner;
- `gdlint`/`gdformat` из gdtoolkit только в CI/разработке, после пробного
  прогона и фиксации версии;
- валидатор всех определений, ссылок, локализационных ключей и арт-профилей;
- debug overlay/console, структурированные логи, хэш доменного состояния
  и «bug bundle» для воспроизведения конкретного мира;
- fixtures старых сейвов и тесты миграций;
- harness для двух процессов host/client и сценариев отключения;
- отдельная benchmark/soak-сцена для бюджетов производительности.

GodotSteam, LimboAI, Dialogue Manager, State Charts, GDExtension/C++ и
Git LFS остаются поздними решениями под измеренную боль или конкретный
срез.

## 1. Главный принцип: маленькое ядро, стабильные швы

Core не должен стать универсальным «движком миров» на все случаи жизни.
Такая платформа заранее почти всегда угадывает не те абстракции. Мы
строим маленькое ядро вокруг нескольких стабильных контрактов:

1. **Состояние мира — сериализуемые данные, а не дерево нод.**
2. **Определения контента неизменяемы в runtime; состояние ссылается на
   них по стабильным ID.**
3. **Внешний ввод и решения NPC становятся командами/намерениями;
   успешные изменения мира фиксируются фактами.**
4. **Один авторитетный писатель состояния на хосте.** Презентация, клиенты
   и фоновые задачи не меняют мир напрямую.
5. **Симуляция разделена на доменные системы с собственной частотой и
   бюджетом, а не на `_process()` сотен нод.**
6. **Ноды Godot — представление активной области.** Они могут исчезать,
   заменяться и перерисовываться другим артом без потери мира.
7. **Сеть, сохранения, арт и плагины — адаптеры за интерфейсами.**
8. **Каждая схема данных версионируется с первого дня.**
9. **Случайность воспроизводима:** именованные RNG-потоки, состояние
   которых сохраняется; глобальный `randf()` в доменной симуляции запрещён.
10. **Производительность измеряется, а не угадывается.** Многопоточность,
    бинарные форматы и нативный код вводятся только после профайлера.

Внутренний алгоритм конкретной системы можно переписать. Нельзя без
миграции ломать ID, схемы состояния, смысл фактов, протокол команд и
границу состояние/презентация.

## 2. Слои фундамента

```text
Godot shell
  main scene, menus, settings, audio, scene loading
        |
GameSession / composition root
  собирает одну кампанию и владеет сервисами сессии
        |
        +--> Presentation (ноды, чанки, ActorView, UI, звук)
        +--> Network adapter (ENet сейчас, Steam возможен позже)
        +--> Persistence adapter (codec + atomic store + migrations)
        |
Authoritative Simulation
  scheduler -> commands -> domain systems -> facts
        |
WorldState + DefinitionRegistry
  изменяемое состояние кампании + неизменяемые определения контента
```

### 2.1. Godot shell и автозагрузки

Существующие автозагрузки остаются оболочкой приложения:
настройки, аудио, загрузка сцен и состояние меню/паузы. Они не станут
владельцами мира.

`EventBus` допустим для UI/app-событий, но не является журналом фактов и
не хранит правду симуляции. Текущий слотовый `SaveSystem` — только
заглушка меню; сохранение кампании получит отдельный `SaveStore` и
доменные codec-классы.

### 2.2. GameSession как composition root

Одна запущенная кампания собирается явно одним объектом сессии. Он
создаёт и связывает:

- загруженный `DefinitionRegistry`;
- `WorldState`;
- `WorldClock` и именованные RNG-потоки;
- планировщик доменных систем;
- очередь команд и `FactLog`;
- persistence-сервис;
- сетевой endpoint хоста/клиента;
- презентационный слой активной области.

Это лучше десятка новых автозагрузок: сессию можно создать headless в
тесте, запустить host и client в разных процессах и не тащить глобальное
состояние между мирами.

## 3. Контракты расширения

### 3.1. Стабильные ID и пакеты определений

Каждый вид, материал, предмет, рецепт, черта, проект, культура, якорь и
сценарий получает полностью квалифицированный ID вида:

```text
core:species/navelu
core:material/torava_wood
core:project/restore_side_pond
```

Правила:

- ID никогда не переиспользуется после удаления контента;
- переименование делается таблицей алиасов/миграцией, а не тихой заменой;
- состояние и сейв хранят ID и экземплярные данные, а не ссылку на
  Godot Resource;
- пакет контента имеет manifest: ID пакета, версия, диапазон схем,
  зависимости и хэш содержимого;
- официальный контент `core` проходит тот же загрузчик и валидатор, что
  будущие data-моды.

JSON является каноническим авторским/внешним форматом определений.
После загрузки JSON компилируется в проверенные типизированные объекты
реестра. Валидатор обязан ловить дубли ID, битые ссылки, диапазоны чисел,
отсутствующие ключи локализации, неизвестные теги и отсутствующие
визуальные профили до запуска мира.

### 3.2. WorldState: изменяемая правда кампании

`WorldState` — обычная модель данных без Node-ссылок. Внутри:

- версия схемы, campaign ID, Genesis Seed и manifest пакетов;
- игровое время и состояние RNG-потоков;
- чанки и экологические ячейки;
- актёры и их компонентные подсостояния;
- дома, поселения, запасы, проекты и соглашения;
- разреженные отношения, знания, слухи и репутация;
- якоря, окна и карантинные состояния;
- FactLog/хроника и следующий runtime entity ID.

Runtime entity ID выдаёт только хост и сохраняет счётчик в сейве.
Definition ID отвечает на вопрос «что это за вид/предмет», entity ID —
«какой именно экземпляр живёт в этой кампании».

**Текущий срез P0-D:** в коде уже есть campaign ID, Genesis Seed,
сортированные pins пакетов, WorldClock/RngStreams/FactLog, allocator и
generic JSON-safe компоненты runtime-сущностей. Чанки, актёры,
поселения, отношения и якоря из списка выше остаются целевыми
доменными подсостояниями следующих срезов, а не уже готовой симуляцией.

Состояние кодируется явными codec-функциями по подсистемам. Нельзя
сохранять целые Node/Object или надеяться, что произвольный Dictionary
сам переживёт годы разработки.

### 3.3. Чанки, экоячейки и гидратация

Стартовые размеры Baseline: чанк мира 128 м, экологическая ячейка 32 м.
Они являются параметрами прототипа, а не вечным законом физики.

Статичная топология долины может восстанавливаться из курируемых данных
и Genesis Seed. В сейве хранятся изменяемые поля и дельты: влага,
плодородие, популяции, вырубка, постройки, гари, следы и другие поля,
зарегистрированные системами.

Гидратация — создание нод и отдельных тел около игроков. Дегидратация —
обратный перевод в агрегаты. Для популяций обязательный инвариант:
переход aggregate <-> individual не должен размножать или терять
существа/биомассу без записанной причины. Этот инвариант тестируется
раньше красивой анимации.

### 3.4. Команды, намерения и факты

Игрок и NPC не меняют мир прямым вызовом случайных нод.

- Клиент или локальный ввод создаёт **намерение**: «идти туда»,
  «взаимодействовать с entity X глаголом Y», «начать проект Z».
- Хост проверяет отправителя, дистанцию, состояние тела, права, ресурсы,
  кулдауны и правила кампании.
- Принятое намерение становится **командой** авторитетной симуляции.
- Результат записывается как **факт**: кто, где, когда, с чем и какой
  исход. Факт не равен знанию NPC: наблюдения, слухи и убеждения хранятся
  отдельно.

Новая игровая возможность добавляется новым типом команды, её
валидатором, эффектом, фактами, презентацией и тестами. Общий сетевой
конверт и цикл симуляции при этом не переписываются.

FactLog не обязан быть полным event-sourcing: источником загрузки
остаётся снимок состояния. Факты нужны хронике, социальной памяти,
отладке, репликации значимых изменений и bug bundle. Старые факты можно
сворачивать в хронику/итоги по политике удержания.

### 3.5. Доменные системы и планировщик

Планировщик вызывает системы по доменному времени, а не по FPS:

- активные тела/локальные процессы — часто, но в бюджете;
- вода, популяции, запасы и маршруты — по часам;
- дома, проекты, слухи и роли — по дням;
- климат, политика и сезонные пересчёты — по дням/сезонам.

Каждая система владеет своим подсостоянием и имеет явный порядок в
общем проходе. Ориентир порядка: время -> погода/вода/почва -> экология
-> труд/проекты/запасы -> знания/репутация/политика -> якоря -> сводки и
хроника. Точный порядок фиксируется кодом и тестами, а не порядком нод в
сцене.

Для региональной симуляции важна воспроизводимость: одинаковое
состояние + одинаковые команды + одинаковые RNG-потоки должны давать
одинаковый доменный результат и хэш состояния. Физика и анимация на
клиентах не обязаны быть бит-в-бит детерминированными, потому что они
не владеют правдой кампании.

Полный ECS-фреймворк в P0 не вводим. Начинаем с реестров, типизированных
массивов/словарей по ID и компонентных подсостояний актёров. Если
профайлер покажет горячий участок, его можно перевести на packed arrays
или нативный код локально, не меняя внешние контракты.

### 3.6. Компоненты актёров и поля мира

Новая способность не должна требовать расширения одного гигантского
класса персонажа.

Актёр состоит из явно кодируемых компонентов: тело/позиция, нужды,
навыки, раны, инвентарь/экипировка, социальная идентичность, знания и
текущая задача. Болезнь позже добавляется новым компонентом, системой и
миграцией со значением по умолчанию.

Экоячейка аналогично имеет зарегистрированные поля: влага, плодородие,
покров, популяции по видам/стадиям, загрязнение/инвазия и следы человека.
Новое поле добавляется с codec, default-значением, миграцией и системой,
которая его обновляет.

Компоненты не превращаются в бесконтрольный мешок Variant: каждый
известный компонент имеет схему, версию, владельца-систему и тесты.

### 3.7. Презентация и арт

Состояние знает вид, стадию роста, здоровье, сезонный вид и позицию.
Презентация переводит это в спрайты, TileMapLayer, инстансированную
растительность, частицы, звук и анимацию через визуальный профиль
определения.

Следствия:

- смена художественной техники не переписывает экологию;
- один вид может иметь стадии молодое/зрелое/больное/сухое/срубленное;
- чанк можно перерендерить другим способом после perf/art-spike;
- `MultiMeshInstance2D` или другой батчинг — деталь презентационного
  слоя, а не модель популяции.

### 3.8. Сеть

Транспорт скрывается за интерфейсом endpoint: host, join, send,
disconnect и сигналы соединения. P0-реализация — ENet. Поздний
Steam-транспорт должен заменить реализацию peer, а не симуляцию.

Протокол с первого дня имеет:

- версию протокола;
- handshake с версией игры, схемой мира и manifest/hashes пакетов;
- конверт сообщений `kind + tick + payload`;
- unreliable-поток для частых transform-снимков;
- reliable-поток для команд, фактов, инвентаря, политики и снимков;
- interest set по актёрам/чанкам каждого клиента;
- проверку отправителя на хосте для каждого намерения.

Автоматическая синхронизация всех свойств нод не используется как
основа мира. Одиночная игра проходит тот же авторитетный путь локально.

### 3.9. Сохранения и миграции

Три схемы Baseline сохраняются отдельно: персонаж, мир и наследие.
Каждая имеет заголовок: формат, версия схемы, версия игры, manifest
пакетов, время создания и checksum.

Запись мира:

1. сериализовать временный снимок;
2. записать во временный файл в том же каталоге;
3. закрыть и проверить файл/checksum;
4. ротировать предыдущий валидный снимок в backup;
5. заменить текущий файл временным;
6. при загрузке сначала мигрировать и валидировать во временное
   состояние, только потом заменять активную сессию.

Миграции идут по одному шагу `v1 -> v2 -> v3`. В репозитории хранятся
минимальные fixtures старых форматов. Формат payload в P0 может быть
JSON; если размер/скорость станут проблемой, codec позволит перейти на
сжатие или бинарную кодировку без изменения доменной модели.

**Реализовано в P0-D:** мировой конверт v1, payload SHA-256, миграция
fixture `v0 -> v1`, generic `SaveStore` с временной записью, проверкой
байтов, ротацией backup и recovery. Отдельные персонаж и наследие ещё
не выдуманы как пустые схемы: они получат собственные codec поверх того
же `SaveStore`, когда появятся доменные модели. Проверку совместимости
package pins с фактически загруженным реестром добавит P0-E при старте
сессии.

## 4. Планируемые границы кода

Папки создаются по мере P0, а не как пустая «архитектура ради папок»:

```text
scripts/
  autoloads/          # только shell приложения
  app/                # Main, GameSession, bootstrap
  core/               # IDs, clock, RNG, facts, scheduler, registry, codecs
  domain/             # environment, ecology, actors, settlements, politics, anchors, combat
  net/                # transport interface, ENet adapter, replication
  persistence/        # SaveStore, schema codecs, migrations
  presentation/       # chunk/actor views, camera, vegetation, effects
  ui/                 # экраны и HUD поверх запросов/команд

data/core/            # официальный пакет определений и manifest
tests/
  unit/               # registry, RNG, clock, codecs, migrations
  integration/        # host/client, save recovery, command scenarios
  soak/               # долгие детерминированные прогоны мира
  fixtures/           # старые сейвы и битые данные
```

## 5. Как будем вводить будущие системы

| Будущее добавление | Что добавляется | Что не должно переписываться |
|---|---|---|
| Новый вид | JSON-определение, связи пищевой сети, визуальный профиль, тесты баланса | реестр, сейв, сеть, планировщик |
| Болезнь | компонент актёра/популяции, система распространения, факты, миграция default | общий Actor, экологический цикл целиком |
| Новый проект поселения | определение проекта, требования труда/материалов, эффект, UI решения | система выборов и все поселения |
| Новая боевая техника | определение/условия практики, команда/эффект, анимация/звук | сеть, навыки как система, сейв персонажа |
| Новая экспедиция | пакет региона/видов, якорь и правила окна, карантинный профиль | домашний мир и Core-симуляция |
| Act II | новый контентный пакет, системы угрозы, миграция состояния Act I | ID мира, дома, хроника, персонажи |
| Steam-транспорт | новый adapter peer и handshake transport details | команды, репликация, симуляция, сейвы |
| Новый арт-стиль | визуальные профили и presenters | WorldState, экология, баланс |
| Data-мод | пакет JSON с manifest и namespace | официальный загрузчик и валидатор |

## 6. Современный инженерный контур

### Нужно в P0

- зафиксированная версия Godot и официальный бинарь в CI — уже есть;
- собственный fallback runner для первых контрактов уже работает; спайк
  GdUnit4 6.2.x на 4.7.2 остаётся перед сценовыми/input/mock-тестами;
- тесты реестра, RNG, часов, команд/фактов, codec и миграций;
- валидатор данных одной командой и в CI;
- debug overlay: время/tick, чанк, активные тела, пиры, бюджеты систем,
  последние факты, хэш доменного состояния;
- dev-сценарии с фиксированными сидами: пустой greybox, два игрока,
  краш во время сохранения, битый JSON, отключение клиента;
- структурированный лог сессии и экспорт bug bundle.

### Нужно по ходу P1–P3

- benchmark-сцена активных тел и растительности;
- soak-прогоны на нескольких сидах в headless;
- сетевой harness из двух процессов, позже — искусственная задержка и
  потеря пакетов;
- визуальный инспектор чанка/экоячейки и графа видов как dev-инструмент;
- правила импорта арта/аудио, атласы, бюджеты текстур и проверка ссылок;
- автоматическая проверка локализационных ключей RU/EN.

### Не сейчас

- C# или C++ ради «современности»;
- полный ECS, универсальный event-sourcing или собственная БД;
- многопоточная запись симуляции;
- публичный сервер, матчмейкинг и облачные сейвы;
- crash-reporting сервис без релизной политики приватности;
- скриптовый моддинг до стабильной схемы данных 1.0;
- Git LFS до появления тяжёлых бинарных ассетов.

## 7. Порядок строительства P0

1. **P0-A. Гигиена каркаса — реализовано:** InputMap, 2D-слои,
   собственный test runner и gdtoolkit 4.5.0 в CI по всем first-party
   GDScript.
2. **P0-B. Примитивы — реализовано:** stable ID, JsonValue, WorldClock,
   RNG streams, FactLog и state hash с unit-контрактами.
3. **P0-C. Определения — реализовано:** manifest, loader, registry,
   validator и первый официальный пакет `data/core` из трёх видов и двух
   материалов.

**Hardening-gate перед P0-D — пройден.** До появления сейвов исправлены
дешёвые сейчас и дорогие позже контракты: пустые сегменты StableId,
ключей локализации и путей пакета отклоняются; JSON-граница ограничивает
глубину/циклы и точный integer-диапазон; RNG state хранится строкой i64 и
выводится SHA-256, а не `String.hash()`; WorldClock/RngStreams/FactLog
имеют versioned snapshots и не портят текущее состояние при битом
restore; StateHash различает типы ключей и точно кодирует float.
Сознательно не делались раньше времени per-kind схемы контента,
проверка существования переводов/арта, настройка клавиш по плейтесту,
GdUnit4, экспортный билд и perf-бенчмарки — им нужны соответствующие
игровые срезы, а не абстрактная полировка примитивов.

4. **P0-D. Состояние и сейв — реализовано:** минимальный WorldState,
   codec v1 с checksum, atomic SaveStore, recovery из backup и fixture
   миграции `v0 -> v1`; отдельный persistence runner зелёный в CI
   `39632507068`, последующий hardening-gate — в CI `39634544055`.
5. **P0-E. Авторитетная сессия:** scheduler, команды/намерения, локальный
   хост и ENet-клиент, два тела и один изменяемый объект мира.
6. **P0-F. Greybox-презентация:** чанк, ActorView, Camera2D, debug overlay.
7. **P0-G. Приёмка:** unit/integration/soak-smoke, краш сейва, битый JSON,
   отключение клиента, одинаковый мир у host/client.

### Постоянный quality gate после каждого этапа

По правилу автора каждый значимый срез закрывается не первым зелёным
CI, а коротким профессиональным self-review: контракты/типы на границах,
потеря данных и crash-окна, битый ввод, безопасность путей, горячие пути
и пробелы тестов. Доработки делаются только там, где риск дёшево закрыть
сейчас и дорого — после появления потребителей. Затем проверки и CI
повторяются, документация синхронизируется, и только зелёный gate даёт
переход к следующему этапу без отдельного ожидания. Красный gate или
продуктовый вопрос останавливают переход и требуют доклада автору.

## 8. Честная граница обещания

Полностью без переписываний игру такого масштаба не строят. Прототипы
обязательно покажут, что часть внутренних алгоритмов и представлений
нужно заменить. Задача фундамента — чтобы эти замены были **локальными**:

- алгоритм популяции можно заменить внутри ecology;
- renderer чанка можно заменить внутри presentation;
- ENet можно заменить Steam-транспортом;
- JSON payload сейва можно сжать или сделать бинарным;
- планировщик задач NPC можно заменить, не меняя дома и факты.

Если изменение требует трогать ID, схемы, факты, протокол или границу
состояние/презентация, оно оформляется как архитектурное решение с
миграцией и тестами, а не как тихий рефакторинг.

## 9. Открытые технические спайки, не блокирующие старт

- GdUnit4 против расширения собственного runner/GUT — отдельный спайк
  перед сценовыми/input/mock-тестами; первые контракты уже не ждут его.
- Точный payload сейва после измерения размера: JSON, compressed JSON
  или бинарная кодировка за тем же codec.
- Представление террейна в презентации: TileMapLayer, custom mesh или
  гибрид — после art/perf-spike.
- Точные частоты доменных тиков и размеры interest area — после P0/P1
  нагрузочных тестов.
- Внутреннее представление популяций в горячих циклах — после первого
  экологического soak-теста.

Эти вопросы специально оставлены за швами. Они не требуют откладывать
P0 и не должны решаться покупкой ещё одного универсального плагина.
